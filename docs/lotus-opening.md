# LOTUS: a separate 3.2-second opening

Scope: preview only, after `46e5290`. The model, morph geometry, materials, lighting, background/label contrast, settled camera and existing project/reader transitions are retained. Backup: `backup/pre-lotus-opening-2026-11-05`. Production remains unchanged.

The renderer reports readiness only after the GLB is downloaded, decoded, compiled and its initial GPU work completes. The existing transfer/prepare indicator then disappears. A separate GSAP timeline holds the bud for 0.4 seconds, unfolds it for 2.2 seconds, and settles the remaining 3% with labels/product thumbnails over 0.6 seconds. Five morph weights have 50 ms offsets contained within the unfolding interval. The camera/scale follows the same overall opening envelope. Total duration is 3.2 seconds; loading speed does not stretch or compress it.

Tap/click on the scene, Escape and the localized skip button complete the current pose in 180 ms. That input is consumed before petal selection. Navigating directly to a project or opening the gallery also ends the intro; scene identity and session completion survive project, reader, gallery and history returns. Locale changes cannot restart the timeline. Reduced motion prepares the open pose before its first visible frame and uses only a 180 ms appearance. Repeat visits in the same tab use that short appearance too. The model still has to load honestly if it is not cached. Focus moves to the project navigation if the focused skip control disappears on completion.

`tests/lotus-opening.browser.ts` covers delayed real GLB transfer, a controlled 50 ms sampling grid for phase durations, stationary bud, staggered morphs and final-phase label reveal on desktop/mobile, Escape/touch/keyboard skips, early project/gallery navigation and history without remounting the canvas, reduced motion, session visits, language changes and focus retention. Existing tests cover fallback, all routes/languages, continuous transitions, reader fitting, typography and contrast. The initial reduced-motion test caught a stale closed-bud warmup frame; preparing its open pose before warmup fixed it.

The proof page `proofs/lotus-opening/` contains uncut ordinary-speed first-entrance recordings and timing metadata. Recordings use installed headless Chrome on Windows, hardware AMD Radeon WebGL through ANGLE Direct3D11, fresh contexts/cache, no CPU or network throttle, at 1440×900 and touch-emulated 390×844. The video is 25 fps and is not a physical-display performance benchmark. Physical Android/iPhone and Safari remain untested. Intermediate frames of both recordings were visually reviewed separately from assertions.

No paid generation. Known project spend remains 6 of 60 Higgsfield credits.

Final recording timings: desktop 3200.7 ms, mobile viewport 3203.7 ms. These are wall-clock animation durations, not FPS measurements; full readiness/start timestamps are in the recording metadata.

Quiet appearances keep surface input available. The surface regression explicitly waits for model readiness: reduced motion now prewarms an open flower while the canvas is still hidden behind the real loading state. An open morph value alone is not a readiness signal.

## CI follow-up

The first CI attempt exposed a real renderer difference, not a model or navigation reset: a free-running Windows SwiftShader probe produced only 21 frame samples during a 3260.9 ms opening and took 442.4 ms to finish the cached appearance. CI observed 1-2 samples in the short bud hold and some Playwright actions arrived after the intro had naturally completed. A reader assertion likewise counted 19 samples instead of an assumed 20. These are not evidence of hardware-display smoothness.

The quiet appearance now uses composited native opacity animations and avoids no-op pose/focus tweens, so a stationary flower is not repeatedly redrawn just to fade in. In the same separate free-running probe, cached appearance improved to 291.2 ms on SwiftShader; reduced motion was 251.1 ms. Hardware AMD ANGLE measured 3202.3 ms for opening and 192.6 / 193.4 ms for cached / reduced appearance, with no main-thread long task during those measured windows. The software opening remained sparse (22 samples in 3251 ms); the project does not claim smooth physical-device rendering from this test.

State/interaction regressions now use Playwright's installed clock to inspect explicit 50 ms opening steps and 20 ms interrupted reader steps, including real WebGL geometry. They retain the same phase, monotonicity, overlap, proportions, focus and history assertions. They do not claim FPS or wall-clock performance. All nine affected scenarios passed both hardware Chrome and forced SwiftShader locally; hardware first-entry recordings and the free-running probe provide separate timing evidence. No test was skipped and no contrast or geometry threshold was relaxed.

The next CI runs passed 42 of 43 checks: the remaining check conflated a native opacity animation's 180 ms active duration with delivery of its completion callback. Linux software rendering reported callbacks after 434.7 and 502.9 ms. A Windows SwiftShader probe with 4× CPU slowdown reproduced 504.5 ms, including an initially pending animation and a 438 ms gap between frame callbacks, with no reported main-thread long task. Assigning one explicit document-timeline start removes the pending-start wait and keeps the canvas and five labels synchronized. Software rendering can still delay frame/callback delivery (558.9 ms in a repeat slowed probe); this is an explicitly retained limitation, not a claim that every device completes visually in 180 ms.

The free-running quiet-appearance regression now retains the actual native Animation objects and checks all six effects: 180 ms duration, zero delay, one iteration, identical resolved start, opacity-only keyframes, finished state, and an open stationary flower throughout. It attaches the observed callback elapsed time separately. The former arbitrary 400 ms CI wall-clock assertion was replaced with those motion-contract checks, not a larger threshold. Ordinary-speed hardware timing remains a separate real-time check, including verification of the published site. The normal 3.2-second opening code and recordings are unaffected by this quiet-mode refinement.
